# Безопасность

## Редактируемый текст

Читать `siteContent/giftGuidance` может любой посетитель; создавать и обновлять — только администратор; удалять нельзя. Правила принимают только поля `things`, `brands`, `updatedAt`, ограничивают строки 4000 символами и требуют timestamp. Клиент выводит значения через `textContent`, поэтому введённая HTML-разметка не исполняется.

Резервный `data/firestore-snapshot.json` содержит только и без того публичные данные сайта. Пароли, токены Firebase CLI, OAuth-данные и ключи service account в него не попадают.

## Фото в публичной версии

- В репозиторий и на сайт попадает только оптимизированная копия `dist/assets/hero.jpg`, повторно сохранённая без EXIF и другой исходной метаинформации.
- Исходное фото, рабочие варианты и скриншоты исключены из Git и остаются только локально.
- Поскольку страница публичная, посетитель технически может сохранить показанную hero-копию. Запретить это средствами HTML/CSS невозможно; защита строится на том, что оригинал и его метаданные не публикуются.
- Публичная и административная страницы задают одинаковые директивы для `robots`, `googlebot` и `bingbot`: `noindex`, `nofollow`, `noarchive`, `noimageindex`, `nosnippet` и запрет превью. Добросовестные поисковые роботы не должны индексировать страницы и hero-изображение.
- `dist/robots.txt` дополнительно содержит `Disallow: /`. Для project-site GitHub Pages файл публикуется внутри `/birthday-wishlist/`, тогда как стандартный robots-файл читается только из корня домена. Поэтому основная защита от индексации здесь — meta robots на каждой HTML-странице; GitHub Pages не позволяет проекту задать `X-Robots-Tag` для ответа. Абсолютной приватности это не даёт: для неё нужен закрытый хостинг или серверная авторизация.

## Граница доверия

Клиентский JavaScript считается недоверенным. Все реальные права и ограничения задаются в `firestore.rules`. Публичная Firebase web-конфигурация не является паролем и может находиться в статическом файле; учётные данные администратора и service-account ключи в репозиторий не добавляются.

Рабочая админка не выполняет автоматическое стартовое заполнение; пустая коллекция остаётся пустой.

## Права

- Читать `gifts`: любой посетитель.
- Менять только `status` существующего подарка: любой посетитель. Поле `category`, как и все остальные поля, анонимному пользователю менять нельзя.
- Создавать, полностью редактировать и удалять: только пользователь с техническим email `admin@birthday-wishlist.local`. Для delete проверяется только административная сессия: `request.resource.data` при удалении отсутствует и не участвует в валидации.
- Все остальные коллекции и документы: запрет по умолчанию.

Даже если злоумышленник вызовет Firebase API напрямую и зарегистрирует другой аккаунт, правила не дадут ему административных прав. При расширении команды технический email нужно заменить UID allowlist или custom claims.

Админка запрашивает только пароль. Для Firebase Auth используется неперсональный технический адрес `admin@birthday-wishlist.local`, зафиксированный в клиентском коде; он не является секретом и не раскрывает личную почту владельца.

## Серверная валидация

Правила проверяют белый список полей, типы, длины, диапазоны, допустимый статус, фиксированный набор значений `category` и тип `createdAt`. Для публичного обновления используется `diff().affectedKeys().hasOnly(['status'])`, поэтому прямой запрос на изменение категории отклоняется.

Цена принимает `null` либо целое число 0–9 999 999 включительно. Ограничение действует и в UI, и в Firestore; анонимный посетитель по-прежнему не может менять цену.

## Осознанное ограничение

Гости не авторизуются, поэтому система не знает, кто поставил бронь. По требованию продукта любой гость может снять любую бронь после явного предупреждения. Если понадобится правило «снять может только забронировавший», потребуется анонимная авторизация и отдельный токен владельца брони.

## Контроль перед публикацией

- В Firebase Auth включён только Email/Password.
- Саморегистрация отсутствует в интерфейсе.
- В `dist/assets/firebase-config.js` нет паролей, приватных ключей и service-account JSON.
- `firestore.rules` опубликованы и проверены Rules Playground/Emulator.
- Для Auth включены password policy и email enumeration protection, если доступны в консоли.
- `/admin/` содержит `noindex` и не связан с главной страницей.
- На обеих HTML-страницах присутствуют отдельные директивы `robots`, `googlebot` и `bingbot`; публичная страница по-прежнему не содержит ссылки на `/admin/`.


## Исправления QA от 4 ноября 2026

Сохранение и удаление подарка сериализованы до подтверждения Firestore; смена формы и выход заблокированы. Бронирование и снятие выполняются транзакцией с проверкой прежнего статуса, конфликт не сообщает об успехе. Это разрешение конкуренции транзакцией, без добавления серверных полей блокировки. Автоматического seed в рабочем клиенте нет; схема и правила доступа не менялись. Панель фильтров находится в обычном потоке на всех ширинах. Закрытые описания inert и aria-hidden; заголовок содержит отдельную кнопку раскрытия. Escape и уход фокуса закрывают меню. Ошибки редактора выводятся внутри диалога, общие уведомления закреплены внизу окна. Загрузчик bootstrap.js обрабатывает отказ импорта и ожидание более 15 секунд с кнопкой повтора.
