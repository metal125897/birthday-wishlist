# Архитектурные решения

## ADR-001 — статический frontend + Firebase

**Статус:** принято.

Выбрано вместо собственного сервера, чтобы сохранить нулевую стоимость, простую публикацию и общую постоянную базу. GitHub Pages отдаёт файлы, Firebase отвечает за данные, авторизацию и серверные правила.

## ADR-002 — нативный JavaScript без сборщика

**Статус:** принято.

Для двух страниц и одного небольшого data flow сборщик не даёт достаточной пользы. Browser modules уменьшают количество инфраструктуры и делают публикацию папки `dist/` прямой.

## ADR-003 — первичное заполнение после входа администратора

**Статус:** принято.

Анонимный клиент не имеет права создавать документы. Поэтому канонические 57 подарков записываются batch-операцией при первом входе владельца в пустую базу. Детерминированные ID и проверка пустой коллекции защищают от дублей.

## ADR-004 — администратор определяется техническим email

**Статус:** принято.

В интерфейсе вводится только пароль, а Firebase Auth использует неперсональный адрес `admin@birthday-wishlist.local`. Firestore проверяет этот email в токене, поэтому регистрация произвольного аккаунта через API не даёт прав администратора. При расширении команды перейти на UID allowlist или custom claims.

## ADR-005 — Sites не используется как production-хост

**Статус:** принято по требованию доступности в РФ.

Локальная разработка выполнена по workflow Sites, но итоговая публикация направлена на GitHub Pages/GitLab Pages и Firebase.
